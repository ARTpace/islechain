## 2. 共同架构问题

### 2.1 单体文件问题

**问题**：两个项目都将所有代码放在一个 `main.py` 文件中。

**Infinite-Canvas**：
- 14,934 行 / 674 KB / 490 函数 / 69 类 / 147 路由
- 所有业务逻辑、数据模型、路由处理都在一个文件中

**art-canvas**：
- 11,307 行 / 474 KB / 256 函数 / 70 类 / 210 路由
- 所有业务逻辑、数据模型、路由处理都在一个文件中

**共同痛点**：
1. **定位困难**：找一个端点要在 1 万多行里搜索
2. **合并冲突**：多人协作时几乎必冲突
3. **无法复用**：业务函数与 FastAPI 路由耦合
4. **测试困难**：没有清晰的边界，单测只能端到端跑
5. **AI 协作难**：上下文窗口会被整个文件填满

### 2.2 数据模型问题

**问题**：两个项目都将所有 Pydantic 模型放在同一个文件中。

**Infinite-Canvas**：65 个 Pydantic 模型
**art-canvas**：70 个 Pydantic 模型

**共同痛点**：
1. **模型分散**：模型定义在文件各处，难以查找
2. **重复定义**：可能存在相似模型重复定义
3. **缺乏分类**：没有按业务域组织模型

### 2.3 路由组织问题

**问题**：两个项目都将所有路由放在同一个文件中。

**Infinite-Canvas**：147 个路由
**art-canvas**：210 个路由

**共同痛点**：
1. **路由混乱**：不同业务域的路由混在一起
2. **缺乏分组**：没有按功能模块组织路由
3. **中间件重复**：鉴权、日志等中间件重复应用

### 2.4 业务逻辑问题

**问题**：两个项目都将业务逻辑直接写在路由处理函数中。

**共同痛点**：
1. **逻辑耦合**：业务逻辑与 FastAPI 路由耦合
2. **无法复用**：业务函数无法在脚本里独立调用
3. **测试困难**：无法对业务逻辑进行单元测试

### 2.5 配置管理问题

**问题**：两个项目都使用硬编码或环境变量管理配置。

**共同痛点**：
1. **配置分散**：配置项散布在代码各处
2. **缺乏校验**：配置值没有类型校验
3. **环境差异**：开发、测试、生产环境配置混乱

### 2.6 错误处理问题

**问题**：两个项目都使用简单的 try-except 处理错误。

**共同痛点**：
1. **错误类型单一**：大部分错误都转为 HTTPException
2. **缺乏层次**：没有自定义异常类层次
3. **日志不完整**：错误日志缺乏上下文信息

### 2.7 测试覆盖问题

**问题**：两个项目都没有单元测试或集成测试。

**共同痛点**：
1. **无自动化测试**：完全依赖手动测试
2. **回归风险高**：修改代码后无法自动验证
3. **重构困难**：没有测试保障，重构风险大

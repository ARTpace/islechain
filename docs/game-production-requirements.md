# 游戏工程、数据、测试与交付：后续需求文档

> 更新：2026-11-02；状态：部分实现，未完成全部验收；实际边界见开发流程的实现记录。
> 前置：[策划到美术需求](game-pipeline-canvas.md)；实施：[后续开发流程](game-production-development.md)。
> 已有工程文件、内容数据、受控原生 Canvas 模板、多文件候选、按需搜索读取、文件增删移动与局部编辑、语法及受限行为回归修复、固定构建、备份恢复、测试工作台及交付门槛。任意 Agent 命令仍未开放；语法检查通过不代表游戏运行或玩法验收通过。

## 1. 目标和交付边界

在同一项目内完成：**确认策划与资产版本 → 拆解开发任务 → 构建灰盒 → 接入正式资产和游戏数据 → 运行试玩 → 记录问题 → 定向修复 → 回归 → 导出可运行游戏与源码。**

不仅支持从零生成，还必须支持用户继续改游戏、手工编辑、调整数值和恢复旧版本。不能把“生成一次 HTML”当作游戏开发完成。

第一条完整工程链路限定浏览器 2D 单机游戏。当前受控模板采用零第三方运行依赖的原生 Canvas，Python 负责打包、Node 仅检查 JS 语法；不执行工程脚本。TypeScript + Phaser + Vite 仍是后续候选，须补依赖、许可证与执行隔离验证，不代表已经提供。宿主框架无需迁移。

首条链路支持键鼠、基本响应式和明确的触屏支持声明。不支持的设备不得在交付中宣称兼容。多人联机、账号付费、云端后端、原生发行与 Unity/Godot/Unreal 接入分别后置，不隐含承诺。

## 2. 项目与工程管理

- 延续首期 projectId、owner、canvasId、策划版本、assetId 和选用版本，不另建第二套项目身份。
- 一个项目首条链路只有一个活动游戏工程；普通源码与资源目录可以被外部编辑器打开。
- 支持新建受控模板；任意已有工程导入后置，不能把项目包导入等同于支持所有引擎工程。
- 提供制作概览、画布、工程与运行测试入口。概览显示任务、阻碍、缺失资产、待回归项和当前可用版本。
- 文件浏览、文本查看/编辑、搜索、差异查看和构建日志。大文件限量读取，二进制使用预览，不让模型盲读。
- 手工修改须检测文件 hash；AI 应用补丁前核对基线，不覆盖未读或已变化内容。
- 用户修改需求时展示受影响任务和资源，不整项目重生成。

## 3. 代码开发与执行 Agent

### 3.1 任务计划

每个任务包含稳定 taskId、目标、对应 requirementId、输入版本、依赖、预期修改、验收条目和状态。

任务状态为 queued/running/needs_input/blocked/succeeded/failed/cancelled。状态必须来自实际执行；模型口头说完成不能将任务标为成功。

首期 Plan.acceptanceCriteria 当前为文本列表。后续以显式 schema 迁移增加稳定需求/验收 ID；迁移保留文本与映射，不能在严格模型下静默塞字段。内容修订与 schemaVersion 分开。

### 3.2 Agent 工具与边界

- 一个主执行 Agent，具备项目文件读取/搜索/补丁、资产查询/导入、数据校验、构建、启动停止、日志、测试与快照工具。
- 先评估成熟执行引擎，选择一个真正具备工具调用、会话恢复、取消、权限与可分发许可的实现；不预建多供应商框架或多 Agent 协商。
- 任务只传当前所需策划、资产版本、相关代码和问题证据，不把整个项目无差别塞进上下文。
- 同一工程同一时刻只允许一个自动写入任务；只读任务可并行。人工编辑造成冲突时停止应用并保留候选补丁。
- 工具调用、文件差异、命令、退出码、输入版本与产物可追踪；日志脱敏，密钥不进源码或快照。
- 模型输出视为候选指令，工具层校验路径、命令与权限；不能仅靠提示词限制执行范围。
- 默认工作在复制的运行目录和受限执行环境，只读输入版本，输出产物再校验采用。工作目录不是安全隔离边界。
- 未具备有效隔离前只开放文件候选生成及受控模板命令，不开放任意生成代码/命令的无人值守执行。
- 依赖安装脚本、shell 和构建脚本都可能执行代码；应限制网络、凭据、宿主可访问文件与进程权限，不能只按命令名放行 npm。
- 已配置权限内连续执行，不每步打断；新增外部服务、付费调用或越出权限时明确提示。

### 3.3 灰盒与正式实现

先在占位资产下验证主操作、状态流转、胜负与重开；正式交付再检查必需美术资源和实际加载情况。灰盒不冒充美术完成。

支持基于现有代码定向补丁、差异审阅和恢复点。失败保留最后可用构建；不得自动替换选用资产或重装全套依赖来绕过错误。

## 4. 数据管理

“数据”分为项目制作数据、游戏内容配置和玩家存档，生命周期及权限不同。

### 4.1 项目制作数据

- project.json 保持项目身份、关联及当前版本指针的权威来源；任务和运行记录移到独立有界文件，避免日志使其无限增长。
- schemaVersion 升级需备份、校验与失败恢复；旧项目不自动丢字段，遇到未知新版本以只读诊断打开。
- 设计、选用资产、内容数据、源码、构建均有各自修订或 hash；一次运行通过 input-manifest 固定这些输入。
- 关联需求、任务、assetId、datasetId 和测试，提供最小引用查询；不先建设通用知识图谱。

### 4.2 游戏内容配置

- 管理角色数值、敌人、物品、关卡、掉落或对话等本项目实际需要的数据集，首条样例只做角色、敌人和关卡。
- 每个数据集有 datasetId、schemaVersion、revision、行 ID、字段定义、值和引用约束。
- 首版提供基础表格/表单编辑、错误定位、预览差异和 JSON 导入导出；CSV 导入作为下一增量，必须明确列映射和类型转换，不能猜测丢失前导零。
- 支持 string/number/integer/boolean/enum 和受控引用；上下限、必填、唯一与跨表引用由后端及构建前校验。
- 引用资源使用 assetId，构建时解析到固定资源路径；删除被引用的数据或资产时阻止并列出使用方。
- AI 调数值只提交候选补丁，应用前展示差异并校验；结构合法不表示平衡合理，需实际试玩。
- 不直接编辑代码中的散落常量当作数据管理；也不强制把所有游戏状态塞进配置表。

### 4.3 玩家运行数据

- 首条链路提供版本化本地存档，支持保存/载入、重开、清空测试存档和独立存档槽；是否自动存档由游戏策划确定。
- 项目编辑数据与玩家存档隔离，测试运行用独立命名空间，不能覆盖用户试玩存档。
- 存档含 saveVersion，损坏或版本不兼容时提示并允许保留备份后重置，不静默覆盖。
- 导出默认不含个人存档；本地存档不是云同步或防作弊方案，相关需求后置。

## 5. 资产集成与依赖变化

- 工程引用首期已选文件，不让生成器 URL 成为永久运行依赖。
- 每次构建记录 assetId/selectionId/hash/runtimeDestination；复制进构建目录，不覆盖项目原文件。
- 检查运行时素材引用、文件存在、规格和加载结果；未使用的必需资产应诊断，概念图不计入运行时完成。
- 换图、改路径、改数据 schema 或改策划时，标记相关任务与测试待检查。明确记录的依赖可自动关联，推断关系必须标注待确认。
- 没有完整依赖证据时保守执行核心循环冒烟，不声称精确增量回归。

## 6. 构建、运行和预览

- 模板包含锁定依赖、明确的 install/check/build/start 命令和运行配置；不向用户随意拼 shell 字符串执行。
- runId 记录输入快照、命令、进程树、端口、日志、退出码与状态；停止只处理本系统拥有的进程，不误杀其他项目。
- 刷新界面后能重新关联仍在运行的任务；服务重启后无法确认的任务标为 interrupted，不能伪造成功或自动重复付费执行。
- 预览运行在隔离来源，配置 iframe sandbox 与 CSP；避免同时授予可逃逸的同源权限，不将宿主 token 暴露给游戏。
- 运行错误、资源加载失败和未处理拒绝关联 runId/buildId；消息校验来源窗口、通道令牌及运行版本，不只判断 type 字符串。
- 单条日志、总量、截图和录制有上限，默认保留最近结果；清理前显示范围，不删除被版本或问题引用的证据。

## 7. 测试、问题与修复

详细功能、状态、证据和验收见 [项目游戏测试需求](game-testing-requirements.md)，实施见 [测试功能开发流程](game-testing-development.md)。以该专项文档细化本节，不新增平行项目或运行系统。

### 7.1 验证层次

| 层次 | 最少检查 |
|---|---|
| 静态与数据 | 类型、相关逻辑测试、数据 schema、资源引用 |
| 构建 | 构建退出码及产物完整性 |
| 启动 | 页面加载、关键资源加载、首屏、运行错误 |
| 玩法 | 主操作、进程、成功/失败、重开 |
| 视觉与设备 | 目标尺寸截图、遮挡、可读性、键鼠/声明支持的触屏 |
| 存档 | 保存载入、版本不兼容、损坏恢复、测试隔离 |

没有 JS 报错不等于游戏可玩；截图不等于功能验证。视觉质量和乐趣需要人工审阅。

### 7.2 用例与证据

用例包含 caseId、对应 requirementId、前置数据、操作、预期、执行方式和结果。结果区分 passed/failed/blocked/not_run，并标明 automated/agent/manual。

证据记录输入版本、buildId、runId、截图或日志相对路径、实际行为。证据是受版本约束的事实，不沿用到未经验证的新构建。

### 7.3 问题闭环

- 问题包含 issueId、严重性、复现步骤、期望/实际、版本、证据、关联任务与回归用例。
- 用户可在试玩界面提交反馈并附当前截图；不能可靠还原过程时注明需补充复现。
- 修复前创建恢复点并检查基线，提交定向补丁，跑受影响检查和必要核心冒烟。
- 同一问题连续两轮无效后重新定位，第三轮必须有新证据；仍失败则停止自动修复并说明阻碍，不无限循环。
- 关闭问题需要对应回归证据；历史证据保留，不将“已改代码”当成“已修复”。

## 8. 版本、备份与资源生命周期

- 工作状态与可恢复快照分开；snapshotId 固定策划、数据、选用资产、源码和锁文件的清单/hash，不复制无关缓存。
- 首条链路采用清单加内容文件的文件快照，不要求用户安装 Git；Git 协作是后续可选集成。
- 恢复前保存当前未保存或未快照改动，展示将恢复内容；恢复生成新的当前修订，不倒退审计记录。
- 文件复制/多文件恢复用暂存目录、完整性检查和提交指针，失败不产生半新半旧的活动工程。
- 导出备份包含源数据及 hash，可在新项目 ID 下恢复；恢复时重建 owner/画布绑定，不继承原身份或绝对路径。
- 归档、排除、物理删除分别定义。清理仅处理已确认无引用内容；快照和问题证据算引用，首条链路不自动清理。

## 9. 导出与交付

分别提供“可运行 Web 构建”“源码工程包”“项目备份包”，三者不能互相替代。

正式交付包含构建版本、运行方法、设备支持、必要许可证/来源记录、测试摘要与已知限制。未解决的阻断项禁止正式标记完成，可显式导出开发版。

源码包包含源码、配置、内容数据、选用资源和锁文件，不含 node_modules、宿主密钥、个人存档及临时日志。首条链路导出本地包，不自动上传发布。

## 10. 数据目录建议

```text
USER_DATA_DIR/game-projects/<projectId>/
  project.json
  documents/                  # 延续首期
  assets/                     # 延续首期，版本文件不原地覆盖
  game/                       # 当前源码、依赖锁与运行配置
  content/                    # 游戏数据 schema 与数据集
  tasks/<taskId>.json
  runs/<runId>/               # 输入清单、日志、隔离输出、证据
  tests/                      # 产品用例和结果，不等于宿主测试目录
  issues/<issueId>.json
  snapshots/<snapshotId>/
  exports/
```

这里只定义职责，实际字段与数量上限在阶段 G 冻结。只创建当前阶段会使用的目录。宿主仍以现有存储为基础，除非实测证明需要，不引入数据库迁移。

## 11. 贯穿验收场景

源码依据与差异见 [OhMyGame 源码经验](ohmygame-source-lessons.md)。后续额外要求：构建前保存依赖；试玩会话只能操作和清理自己的窗口，清理需等待进行中的 open；按实际能力开放 reset/setSeed/step。恢复需列明排除和不可读文件，未完成恢复阻止其他写操作；恢复后递增 workspaceEpoch 并通知 Agent 重读。预览来源隔离与宿主执行隔离分别验收，不能互相替代。上述要求不强制采用上游 Electron 或 Git 对象存储实现。

沿用首期俯视角探索样例，补充移动、收集、敌人接触扣血、胜负和重开；允许程序几何作为已声明的灰盒或简单动态元素，最终素材按策划确认。

1. 已确认策划与选用资源进入同一工程，能构建运行。
2. 灰盒实现核心循环，正式版本使用对应选用资源。
3. 修改敌人速度数据并校验，行为可在新运行中观察，不改无关代码。
4. 更换头像版本仅更新相应绑定；旧构建仍能按旧输入复现。
5. 发现失败后重开不能重置状态的问题，记录证据、定向修复并通过回归。
6. 人工与 Agent 同改文件触发冲突，手改内容不丢失。
7. 取消/中断不会误杀其他进程，重新打开能识别任务状态。
8. 存档损坏可恢复，测试不覆盖正常试玩存档。
9. 快照可恢复，备份可导入新项目；未保存改动先保留。
10. Web 包可在干净目标环境启动，源码按锁文件构建；离线能力仅在实际检查通过时声明。
11. 越权文件、命令、下载和伪造消息被拒绝；游戏无法读取宿主凭据。

完成必须说明实际执行的测试、人工判断、未验证设备和外部环境限制，不能用静态检查替代游戏验收。

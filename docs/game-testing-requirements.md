# 项目游戏测试：功能需求

> 更新：2026-11-02；状态：核心测试链路已接入，尚未全部验收；能力与验证记录见测试开发流程末节。
> 上位需求：[游戏制作后续需求](game-production-requirements.md)。实施：[测试功能开发流程](game-testing-development.md)。
> 源码经验：[OhMyGame 试玩会话与恢复机制](ohmygame-source-lessons.md)。本文细化后续阶段 L，并贯穿 J、M、N，不新增一套平行项目或运行系统。

## 1. 目标与范围

让创作者在项目内知道：这个版本测了什么、发现什么、如何复现、修复是否有效、能否交付。

流程：**选择构建 → 生成/编辑测试计划 → 检查环境 → 运行用例或人工试玩 → 收集证据 → 登记问题 → 定向修复 → 回归 → 形成版本报告。**

本功能测试的是用户制作的游戏，不是 Art Canvas 自身。宿主单元测试、游戏源码逻辑测试、游戏运行测试分别记录，不能相互替代。

第一条链路支持已确定的 Web 2D 模板、一个浏览器运行适配器、键鼠和视口变化；触屏仅在适配器支持且游戏声明支持时开放。真实移动设备、其他浏览器、原生引擎、联机、长时间压测与云测试集群后置。

## 2. 测试工作台

在同一项目增加测试入口，复用已有工程、预览与问题面板：

- 概览：当前构建、环境、需求覆盖、通过/失败/阻塞/未执行、未关闭问题与待回归项。
- 用例：按玩法、界面、资产、数据、存档、设备分类，支持搜索和筛选。
- 执行：步骤、实际状态、截图、错误与取消，允许从失败步骤建立问题。
- 人工试玩：独立会话，不被自动测试抢焦点或重置存档；一键附当前构建和截图提交反馈。
- 问题与报告：复现、修复关联、回归结果、历史证据与交付结论。

小项目先用列表与详情，不先做复杂仪表盘。画布只显示测试/问题摘要与入口，不把日志和截图塞进节点 JSON。

## 3. 用例与计划管理

### 3.1 用例结构

| 字段 | 要求 |
|---|---|
| caseId / revision | 稳定标识与用例版本 |
| requirementIds | 关联策划验收条目，不因文字排序改变引用 |
| title / category / priority | 名称、分类、是否交付必需 |
| preconditions | 初始关卡、内容数据、测试存档、可选种子 |
| steps | 动作和顺序，显式标记等待条件 |
| expectations | 可观测的预期和判定方式 |
| requiredCapabilities | 键鼠、触屏、DOM、截图、bridge 等 |
| executionMode | automated / agent / manual |
| environmentProfiles | 实际支持的目标环境 |

- 支持手工建用例，AI 从已确认需求提出候选；采用前可编辑，不自动把含糊描述变成通过条件。
- 覆盖状态区分有无用例、是否执行、是否通过；有用例不等于需求已验证。
- 必需项在计划开始时冻结，不能事后删掉失败项提高通过率。变更计划创建新 revision。
- 测试计划选择用例版本、构建和环境矩阵；计划外探索反馈保留但不混入计划统计。
- 不强迫每条用例自动化。缺少可靠观测时转人工或标阻塞，不以模型猜测作为确定断言。

### 3.2 首批用例包

启动和资源加载、开始/暂停、移动与收集、敌人伤害、胜负、重开、HUD/按钮、窗口适配，以及已实现后的存档与载入。

模板用例只为当前游戏实际存在的功能启用；未实现功能标为未覆盖或明确不适用。不适用需有理由与确认，不自动当通过。

## 4. 构建与执行输入

- 正式测试使用固定 buildId、内容 hash、资产清单、策划版本、用例版本和环境；完整输入保存到 testRun。
- 开发服务器/HMR 下的探索结果标为开发观察。构建或运行内容改变后不能并入原正式测试结果。
- 开始前等待相关保存，检查构建、资源与测试能力；依赖不满足时 blocked，不继续执行错误环境。
- 不在执行中替换 buildId；版本恢复和 workspaceEpoch 改变后停止旧会话，晚到回调只记录为过期事件。
- 默认每个会话顺序执行，测试之间清理按键、触点、焦点、页面与测试数据；有状态的多步骤旅程作为单独场景声明。

## 5. 试玩适配器与测试桥

复用 OhMyGame 的行为经验，首版只实现一个 Web 适配器：

- open / inspect / act / capture / close，sessionId 绑定 owner、projectId、buildId、testRunId 与 workspaceEpoch。
- 相邻动作可批量发送；open/act 已返回新观察时不重复无意义 inspect。
- 能力清单决定输入和观察手段，缺失能力明确 unavailable；每批动作数量、单步时长、会话总时长和日志均有上限。
- 同一个自动会话只能有一个输入执行者，人工需要接管时暂停自动执行并记录；不同会话互不关闭。
- 取消后释放已按下键和触点；等待进行中的 open 完成再清理其创建窗口，防止泄漏。
- 可选测试桥提供 reset、setSeed、step、只读状态；仅测试构建启用，采用受控消息和明确 schema，不开放任意 eval 或宿主文件访问。
- 测试桥用于建立条件和观察。玩家操作用例仍通过真实键鼠/触屏触发，不能直接改状态替代操作后宣称功能通过。
- 无确定性桥时记录实际输入与时间；不得承诺随机游戏逐帧重放。种子相同也不意味着不同浏览器必然同帧。

## 6. 结果与判定

执行生命周期 queued/preparing/running/completed/cancelled/interrupted，和结果分开。

用例结果为 passed/failed/blocked/not_run：

- failed：在有效条件下观察到预期不成立，需实际证据。
- blocked：环境、依赖或能力不足，不能判断产品行为；基础设施失败不得直接认定游戏 Bug。
- cancelled/interrupted 执行中尚未形成结论的用例标 blocked 并写原因，其余保留 not_run。
- started 超时需区分等待游戏条件未满足与测试设施故障，保留日志和最后观察。
- 允许显式重跑，保留每次 attempt。重跑通过不能抹去先前失败；反复不稳定标记 flaky，不能静默选最好一次。
- 统计显示计划总数与各类数量；通过率若提供，明确分母，blocked/not_run 不算通过。交付门槛直接检查必需项，不只看百分比。
- AI 视觉判断标注来源和信心不足项，不能作为所有功能的唯一裁判。

## 7. 证据与诊断

每份证据记录 evidenceId、testRunId、caseId、attempt、buildId、时间、类型、相对路径、hash 和采集方式。

最小采集：首屏与失败截图、动作摘要、console error、未处理拒绝、资源加载失败、bridge 状态（若支持）及最后有效观察。

- 截图不等于玩法通过，网络失败不一定导致核心失败；按用例预期判断并保留诊断。
- 保留截图尺寸、视口、设备像素比、浏览器与运行平台版本。时间线关联动作与证据，而不是只留下一个无上下文 PNG。
- 视频/逐帧录制可后置，不能将首版无录制误报为“已自动录屏”。
- 凭据、请求头、用户输入和私人存档脱敏；不将完整抓包或本地绝对路径默认导出。
- 单文件与单次运行容量有上限，达到限制显示证据截断；缺少必需证据时不得静默完成验收。
- 证据先落盘校验后提交索引。问题、快照或报告引用的证据禁止自动清理；缺失时显示损坏并使相应验收结论待复核。

## 8. 视觉、设备与性能

### 8.1 视觉与设备

- 对已声明支持的桌面视口检查遮挡、文本可读性、布局、按钮可达、资源比例与主题一致性。
- 浏览器缩小视口只算响应式模拟，不算真实手机、触屏、GPU 或系统浏览器兼容。
- 截图基线按构建/场景/视口/DPR/渲染环境保存，固定种子与时机；动画区域可声明掩码。
- 像素差异是诊断，不自动等于美术退化；基线更新展示差异并由用户确认，不能失败后自动接受新图。
- 首版采用人工并排检查，自动截图差异在环境稳定后增量开放。

### 8.2 性能

首版按需记录启动耗时、加载失败和可可靠获得的帧时间。采集必须写环境、时长、预热与样本；阈值来自目标设备与策划，不随意承诺 60 FPS。

硬件不同的结果不直接排名。浏览器进程内存不是游戏资源占用的精确值；无可靠指标时标 unsupported。长期泄漏、压力测试后置。

## 9. 问题、修复和回归

- issueId 记录期望/实际、复现步骤、严重性、优先级、输入版本、证据、关联需求与用例。
- 状态 open/triaged/in_progress/ready_for_retest/closed；重复、无法复现、暂缓分别记录理由，不伪装修复。
- 相同错误可提出合并建议，但不同构建/场景保留 occurrence，不仅按错误文案自动合并。
- 用户点击修复后复用开发任务与 Agent，不另建测试专用代码写入器；修复前快照和基线检查。
- 自动修复遵守既有三轮停止规则，不无限重试；失败停在可恢复状态。
- 修复后的新构建重新执行失败用例及直接影响项，必要核心冒烟；未知依赖范围时说明并保守覆盖。
- 关闭必须有新构建回归证据；无变化重复执行不是提高可信度的默认动作。

## 10. 存档、环境和安全

- 测试独立存档槽、存储命名空间和浏览器上下文，重置仅作用于测试环境；人工试玩另开会话。
- 存档功能未实现时用例 not_run/blocked 并写依赖，不宣称通过。
- 测试数据、种子和配置导入需校验，不执行导入包中的脚本。
- owner 校验覆盖用例、执行、证据下载、报告和问题；跨项目 sessionId 拒绝。
- 游戏不能获得宿主身份，试玩消息验证来源窗口、通道、会话和版本；执行隔离继承工程安全门槛。
- 关闭测试只清理其拥有的窗口/进程；预览和其他项目仍可用。

## 11. 数据组织与接口能力

沿用后续项目目录，在 tests 下管理 cases、plans、runs 与 reports；运行证据复用 runs/<runId>/ 的产物，使用 evidenceId 引用，不再维护第二份截图真源。

测试执行 testRunId 关联底层工程 runId，二者职责明确。首版一个底层运行对应一个独立测试会话，避免恢复时状态混淆。

建议资源：test-cases、test-plans、test-runs、evidence、issues、test-reports。开始、查询增量事件、取消、显式重跑分别建操作；写接口带 revision，执行带幂等 requestId，资源 ID 不代替 owner 校验。

所有字段、状态、上限和恢复规则在 T1 冻结，优先复用现有 project/task/run/issue 服务，不先创建通用测试框架。

## 12. 版本报告与完成门槛

报告固定 releaseCandidateId/buildId、输入清单、计划与环境，展示需求覆盖、用例结果、缺陷、证据、人工判断及未验证项。

正式完成至少满足：必需用例在声明的必需环境通过；无未关闭阻断缺陷；证据可读且版本匹配；资产/数据/构建检查通过。任何豁免需明确范围、理由和确认人，属于带限制交付，不能伪装全面通过。

手工填写结果与 Agent 判定保留来源和变更历史。报告形成后不可静默改写，重测生成新版本。支持 JSON 与 Markdown 导出，HTML/PDF 报告后置。

## 13. 首条链路验收

1. 已冻结构建可创建计划、手工编辑用例，记录需求覆盖。
2. 真实键盘完成移动、收集、扣血、胜负与重开，并生成版本关联证据。
3. 注入重开状态未重置问题，测试失败、创建缺陷、修复后回归才能关闭。
4. 资源缺失报告具体路径；环境不可用显示 blocked，不误报游戏失败或通过。
5. 两会话互不污染存档或取消；取消期间 open 返回也能清理。
6. 构建更换和快照恢复使旧执行失效，旧回调不能写入新结果。
7. 失败重跑保留两次记录，flaky 显示不稳定，不只保留通过。
8. 不支持的触屏/真实设备标未验证，视口模拟不冒充设备测试。
9. 人工截图审阅可留下意见；基线不自动接受。
10. 越权证据和伪造会话拒绝，日志脱敏、超限和证据损坏可诊断。
11. 未执行必需项不能生成全面通过报告，干净环境交付验收单独记录。

本次仅定义功能；模拟测试可验证测试平台协议，不能替代实际游戏操作验收。
